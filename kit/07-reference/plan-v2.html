What changed after reading each tool's real docs

  • RocketRide already ships nodes for Cognee, HydraDB and hotdata (tool_cognee, graph_hydradb, db_hotdata). The app is now built as RocketRide agents calling those nodes, not a dashboard over our own glue code.
  • HydraDB is two products. RocketRide's node talks to the hosted memory API, which also gives each user an isolated collection and learns preferences from feedback — exactly what student profiles need. The open-source Cypher database becomes optional.
  • Cognee cannot write into open-source HydraDB. Its Neo4j adapter uses APOC, constraints and UUID ids that HydraDB rejects. We no longer try.
  • Cognee's current API is remember / recall / improve / forget, with sessions, feedback, per-user datasets with permissions, and a strict ontology mode. Those carry the lesson loop and the student profiles.
  • hotdata SQL is read-only; every write is a load. It can create a throwaway database per backtest in under a second, which makes peeking impossible by construction.
  • A Rote Play replays a fixed graph of commands. Course parsing must be one generic script driven by inputs, recorded inside a Rote workspace, or it will not transfer between courses.
  • Everything RocketRide calls must be reachable from its cloud engine. Decide where each piece runs in the first 45 minutes.

The idea

A study planner that learns how exams are written, and how you learn

A student picks a course, uploads the syllabus and anything the professor has said about the exams, and tells Exam Oracle how they like to be taught. It works out how exams in that course are written — which topics always show up, which homework problems come back with the numbers changed, what the last weeks of lectures add — then builds a study plan and practice questions shaped to that student.

It learns on four levels:

  • Per course. Each past exam sharpens that course's prediction.
  • Across courses. Rules about how professors write exams carry to a course it has never seen, so course 3 starts smarter than course 1 did. This is the pitch's spine.
  • Per professor's word. It tests what a syllabus says (“the final emphasizes the last third”) against what past exams did, and learns how much to trust stated guidance.
  • Per student. It remembers how each student likes to learn and updates from feedback (“too wordy”, “that example helped”).

The brief's test: “every run makes the next run smarter, cheaper, more reliable”

What the judges will see improve

A “run” is one backtest: predict one past exam using only what a student would have had before it.

Smarter

% of exam points covered by the top-K topics

Per run, next to two baselines. The key comparison: course 3's first prediction with lessons from courses 1–2 versus blank weights.

Cheaper

Model tokens and minutes per new course

Course 1 is worked out by the agent; later courses replay the Rote loading Play with near-zero model tokens. RocketRide's tracing shows token use per call.

More reliable

First-try check pass rate · Brier score

Loading checks passing first time, leakage checks passing every run, and stated probabilities matching what appeared.

Plus one per-student signal on the demo screen: the preference text before and after a student's feedback. No numbers are promised; the baselines make a modest lift legible.

What each tool really is, how we use it fully, and what bites

How each tool actually works

Each card ends with the 15-minute test its owner runs before building anything on it. Docs = read in the vendor's docs or source; Test = not confirmed, check it first.

Cognee

Structure · builds the course and student knowledge

An open-source memory engine. You hand it text; an LLM extracts the entities and links you define, and it stores them in its own graph (Ladybug), vectors (LanceDB) and metadata (SQLite). Current version 1.5.4 — pin it; four releases landed in two weeks.

How we use it fully

  • remember / recall, the current API the brief asks for, not the legacy cognify/search. Docs
  • Custom graph model (DataPoint classes) with identity_fields on Topic, so one topic is one node however often it is mentioned. Docs
  • Strict ontology per course, built at runtime from the syllabus topic list, so every tag lands on the fixed list; off-list tags are dropped. Docs
  • Datasets with permissions: one shared dataset per course, one private dataset per student; recall(dataset_ids=[course, student]). Docs
  • Sessions → add_feedback → improve(): every backtest is a session scored as feedback, and every student chat is a session whose feedback updates their preference text (PERSONALIZATION_ENABLED=true). Docs
  • Create what you already know (course, term, exam, run) in code and tag with node_set; spend the LLM only on problem → topic tagging.
  • dry_run=True to price an ingest before running it.

Watch out

  • Neo4j provider → open-source HydraDB fails on the first write. Do not wire them.
  • Cost is per-chunk extraction; ~2,000 chunks at 60 requests/minute is 30+ minutes. Pre-split PDFs into one problem + solution per item; set a cheaper LLM_EXTRACTION_MODEL; self_improvement=False during bulk loads.
  • The default PDF loader (pypdf) garbles equations; topic tagging survives it.
  • Ladybug uses file locks: run exactly one Cognee process.
  • The built-in preference node changes ranking, not answer style, and is invisible in results. Keep explicit style in our own StudentProfile and pass it as the system prompt.
  • Merging results across two datasets in one recall is Test; so is forget for one student leaving others' sessions intact.

First testInstall cognee[docs]==1.5.4; define Topic and ExamProblem; remember two problems with dry_run, then for real; confirm a shared topic is one node. Create users admin, s1, s2; grant the course dataset to both; confirm s1 cannot read s2. Run a session, add_feedback("too wordy", 2), improve(), and check the preference text changed.

HydraDB

Memory · durable lessons and student profiles, served to the agent

Two products under one name. The hosted API is a memory service: databases, collections, memories you store and recall, hybrid retrieval, and preference inference from raw text. The open-source Rust database speaks a subset of Cypher over Neo4j's Bolt protocol. RocketRide's node talks to the hosted one.

How we use it fully

  • One collection per student (collection = student id) — the pattern HydraDB's docs recommend. Docs
  • Explicit preferences stored as-is (infer:false) under fixed ids such as s42_pref_pace, so an update replaces the old value. Docs
  • Feedback stored with infer:true, so HydraDB extracts the lasting preference from “too wordy”. Docs
  • The student's syllabus and guidelines ingested as knowledge in their collection.
  • Shared lessons, predictions and run summaries in a shared collection; read with hybrid /query and recency_bias so the newest lessons count most. Docs
  • From RocketRide: store_memory, recall_memory, query_graph, get_schema.
  • Optional Open-source HydraDB for the course graph: algo.MSpaths from this term's topics to past exam problems gives the “why” path and a path-count signal.

Watch out

  • Searching a student's collection and the shared one in a single query is Test; budget two queries.
  • Whether hosted query_graph (or the MCP hydradb_graph_query tool) runs Cypher is Test; the docs disagree.
  • Open-source rules if used: integer node ids plus a key string; only scalar properties; bounded paths (*1..3); no max(); write over Bolt only (HTTP writes return 500 on :latest, issue #196); set RUST_MIN_STACK=33554432 or it crashes on the first query; keep problem text out (strings over ~32 KiB crash a worker).
  • “Git-style temporal versioning” is marketing; there is no point-in-time query. Keep lesson history yourself.

First testpip install "hydradb-sdk>=2,<3"; store one explicit preference and one raw feedback line (infer:true) in collection=s1; query them back; store a lesson in the shared collection; query both collections. From RocketRide, call get_schema and query_graph once to learn what the node really accepts.

hotdata

Insight · signals, echo search, leakage-proof backtests, scoreboard

A query engine (Rust, DataFusion, Arrow) where a database is a disposable scope created in one call. Workspaces share nothing; databases can expire on their own; results are saved and re-queryable. SQL is read-only — data goes in through loads.

How we use it fully

  • A permanent ledger database for all loaded problems, the run log and the scoreboard.
  • One throwaway database per backtest (--expires-at 2h), loaded with only rows dated before the target exam. The model physically cannot see the future. Docs
  • The six signals as saved, versioned queries, run identically in every run database; the query-run history is the audit trail.
  • Homework echoes by hybrid search: bm25_search on cleaned text plus vector_search on a separate table, fused in SQL with reciprocal rank (1/(60+rank)). Docs
  • A leakage assertion inside each run database: latest date < target exam date.
  • From RocketRide: db_hotdata with database_id set to the ledger so results persist between runs.

Watch out

  • No INSERT: write the run log as inline CSV loads (≤ 2 MiB) with idempotency_key=run_id; the first load into a table must be replace.
  • Forks drop indexes; a self-embedding vector index must be the only index on its table.
  • BM25 splits on non-alphanumerics and drops tokens over 40 bytes: store a de-LaTeXed text column.
  • BM25 applies WHERE after taking the top k — over-fetch.
  • Index build time per run is not published Test. If slow, index once in the ledger and date-filter queries instead.
  • hotdata's embeddings are not Cognee's; never mix the vectors.

First testbrew install hotdata-dev/tap/cli, hotdata auth register; create an expiring database; load 50 homework rows and time it; build a text and a vector index with --async and time the jobs; run bm25_search, vector_search and the fused query; append to the ledger twice with the same idempotency_key and confirm no duplicate.

RocketRide

Motion · the student app and the agent pipelines

An open-source pipeline engine (C++ core, Python nodes) with a VS Code IDE. Pipelines are JSON .pipe files of nodes: 15+ LLM providers, document parsers and OCR, agents, tools, memory, vector stores — and nodes for Cognee, HydraDB and hotdata. Apps are React screens deployed to staging.

How we use it fully

  • The sponsor nodes on the canvas: tool_cognee (remember, recall), graph_hydradb, db_hotdata. Docs
  • Their agent, Wave (agent_rocketride), plans parallel tool calls. Cognee's node and the HTTP tool can only be called by an agent. Docs
  • The document parser (or LlamaParse for equations) for syllabi students upload.
  • Webhook sources give each pipeline a public URL plus a key, so the laptop loader can trigger RocketRide after a course loads.
  • Tracing shows tokens per call: run-1-versus-run-N evidence straight from the sponsor's own tool.
  • tool_pipe turns a sub-pipeline into one tool; a tool_python step computes the SHA-256 seal.

Watch out

  • The docs contradict themselves on node names; trust services-catalog.json in your workspace, as the setup guide says. Check the sponsor nodes exist in extension 1.2.0 Test.
  • Auth drops: an empty ROCKETRIDE_APIKEY means “No authorization provided”; fix with pnpm exec rocketride login.
  • Wave is experimental: it needs exactly one LLM and one memory wired in; cap max_waves to protect credits.
  • A chat source needs chat(), a webhook needs send(); mismatches return nothing.
  • The HTTP tool is limited to 10 requests per second.
  • Claim the developer ID on a scratch app first; versions are immutable.

First testpnpm exec rocketride login and confirm the key is not empty; search services-catalog.json for the three sponsor nodes; run a chat → Wave pipeline with an LLM, internal memory and all three sponsor tools, asking it to remember X, recall X, and read both schemas; parse one OCW PDF; deploy a scratch app to @me and confirm credits drop.

Rote (Modiqo)

Muscle memory · course loading and backtests, replayed

Rote records commands you run inside a Rote workspace — shell, API adapters, browser actions — as numbered records, then compiles the successful ones into a Play: a typed-input step graph (main.ts) that replays without the model re-reasoning. Deterministic in method, not in output. Runs locally on macOS or Linux.

How we use it fully

  • Record inside a workspace: rote init oracle --seq, then each step as rote proc run …; export with rote workspace export oracle --params course_url,skip_list. Docs
  • Two Plays: load-course (replayed per course) and run-backtest (replayed every run while the lessons change).
  • Checks as exit codes: numbering and point totals are hard faults; a missing solutions file is “degraded”, not fatal.
  • The resume moment: a hard fault shows the failed step with its evidence, blocks what depends on it, and --resume <run_id> continues. Docs
  • Evidence: rote trace --html (a Gantt of the run) and rote stats.
  • Publish load-course to the Playoffs Community catalog — the Modiqo team's own goal.

Watch out

  • A Play replays a fixed graph. Course-specific improvisation will not transfer, so the splitting and checking logic lives in one generic script driven by inputs.
  • Work done in a plain shell outside Rote, pasted values, or hidden state from earlier runs will not compile.
  • Default step timeout is 30 seconds — raise it for downloads and extraction.
  • Publishing requires a clean run from /tmp: embed or declare scripts; no ./scripts/… paths.
  • Automated calls need --yes --output=json; credentials via rote token set NAME --stdin.
  • No per-run token command is documented: take run 1's tokens from the coding agent, and replays' from the JSON output Test.

First testInstall, rote login, rote whoami --check; run the hello Play twice with --output=json --yes and see what timing and token fields appear; record a two-step workspace that fetches one OCW page; export, lint, replay with a second course URL, then a bad URL — confirm BLOCKED and that --resume works; call it from Python and parse the JSON.

Snyk

Security · continuous, visible, and part of the story

Judges will scan the app and deduct for findings. Snyk connects to Claude Code as an MCP server (Snyk Studio), so the coding agent can scan code and dependencies while it writes.

How we use it fully

  • Snyk MCP in Claude Code; scan on demand with snyk_code_scan and snyk_sca_scan.
  • Two routine scans (hour 1, hour 6): snyk code test --report --project-name=exam-oracle, snyk test --all-projects, snyk monitor --all-projects; each --report adds a snapshot, so the history shows security was continuous.
  • snyk aibom --html lists the models, agent libraries and MCP servers in the stack — an honest architecture slide.
  • snyk_package_health_check before choosing a PDF library.
  • Design out the usual findings: course URLs only from https://ocw.mit.edu with redirects re-checked; files named by hash, never by remote name; Cypher and SQL always parameterised; keys only in environment variables with .env git-ignored from the first commit; never verify=False; LLM text rendered as text, never dangerouslySetInnerHTML; a bearer token on any tunnel.

Watch out

  • npx -y snyk@latest mcp configure --tool=claude-cli writes into Claude's global rules file. Run it only on the hackathon machine, or add the MCP block to the project config by hand.
  • Snyk Code must be switched on in Settings before snyk code test works.
  • Free plan: 100 Code tests a month. The per-edit plugin can burn through them — prefer on-demand scans.
  • No Snyk rule covers prompt injection or an open tunnel; those are on us.

New in v2 — the student layer

Students, syllabi and preferences

What a student gives it

  • The course and exam date, and weekly study hours.
  • How they like to learn: worked examples first or proofs first; short or detailed; visual or verbal; pace.
  • Their syllabus (PDF or text), and anything the professor said about exams: “final is cumulative”, “one cheat sheet”, “the final emphasizes the last third”.
  • Feedback as they study: “too wordy”, “that example helped”, a 1–5 rating.

Where each piece is stored, and how it is used

InputStored inUsed for
Explicit preferencesHydraDB, the student's collection, fixed ids (infer:false); mirrored as a StudentProfile in the student's Cognee datasetThe system prompt for every explanation and practice question; the plan's order and length
Exam date, weekly hoursStudentProfile (Cognee) and a students table (hotdata)Turning the ranked topic list into a day-by-day plan that fits the hours left
SyllabusParsed by RocketRide; remembered into the student's Cognee dataset with a Syllabus model (topics, exam windows, guidelines); kept as knowledge in HydraDBThe course's topic list (becomes the strict ontology) and what each exam covers (the coverage signal)
Professor's stated guidelinesStatedGuideline items (kind, numbers, source) in Cognee; test results in hotdataA seventh signal whose weight is how often stated guidance matched real exams
FeedbackHydraDB (infer:true) and a Cognee session scored with add_feedback, then improve()Updating the student's preferences; the next answer changes

Privacy is part of the design

  • Each student's data sits in their own Cognee dataset and their own HydraDB collection. Shared course knowledge is read-only to students.
  • A student can never read another's data; Cognee raises a permission error, and the smoke test proves it.
  • “Delete my data” uses forget for that student — only after testing that it leaves other students' sessions intact.

Sealing rules — the demo is worthless if the system could have peeked

  1. Every target exam is stored outside the repo and on the load-course skip list.
  2. Each backtest runs in its own hotdata database containing only rows dated before the target exam, plus a check that proves it.
  3. A teammate labels each hidden exam's problems with topics and points before any prediction. The AI never grades itself.
  4. Every prediction prints a SHA-256 hash with a timestamp. At the reveal, recompute it in front of the judges.
  5. Runs only go forward in time.

Simple enough to explain on stage

How the prediction works

Each course has a fixed list of 12–20 topics, taken from the syllabus or lecture calendar before any prediction. Every exam problem, homework problem and lecture is tagged against it. For each topic and target exam, seven signals:

SignalWhat it measuresComputed by
Track recordHow often the topic appeared on earlier exams of the same type, recent terms weighted morehotdata saved query
CoverageInside what this exam covers (from the syllabus; finals cumulative)hotdata, from the Syllabus model
Homework echoHomework problems on the topic that resemble past exam problemshotdata hybrid search
Lecture timeLectures spent on the topic this termhotdata
Untested recent materialFor finals: taught after the last quizhotdata
Already testedWeight on this term's quizzes (learned, either direction)hotdata
Professor said newThe topic falls under a stated guideline, weighted by how often such guidance matched real examsCognee guidelines + hotdata test results
  • The weights are the lessons. After every run, refit them on all runs so far (a small logistic regression over topic rows). Store each as a lesson in HydraDB's shared collection with the runs that support it and a one-line statement.
  • A new course starts from the current lessons, not blank weights. Course 3's cold-start comparison proves it.
  • Score: the share of the hidden exam's points whose topics are on the study list. Baselines on every run: “study evenly” (rank by lecture time) and “copy last exam”. Also topic recall and Brier score.

The Rote Plays

load-course

Input
course_url, skip_list
Steps
Fetch the OCW index → list PDFs → download each (for_each) → extract text → split into problems with points (one generic script) → validate → load rows into the hotdata ledger → remember each item into the course's Cognee dataset → call the RocketRide webhook “course loaded”.
Checks
Hard fault: problem numbers not 1…N, points not matching the printed total, a skip-listed file touched. Degraded: missing solutions file.
Demo
Course 3 is broken on purpose mid-run: BLOCKED with evidence, fix, --resume. Then published to the Playoffs catalog.

run-backtest

Input
course, target_exam
Steps
Create an expiring hotdata database with pre-exam rows → run the saved signal queries → assert no leakage → read the lessons from HydraDB → rank topics → write the prediction and its SHA-256 → score it against the sealed key and both baselines → load the run row → refit lessons → store them in HydraDB → score the Cognee session and run improve().
Why it matters
The same fixed method, replayed about ten times through the day, while the lessons it reads keep changing. That is the compounding chart.

The practice exam is not a Play. It is generated per student inside RocketRide, because it has to change with each student's preferences.

Judge questions

“Isn't this just counting what came up before?”
That's Baseline B, and it's on every chart. The difference comes from homework echoes, untested recent material, trust in the professor's stated guidance, and lessons carried between courses — the cold-start comparison isolates the last.
“How do we know you didn't peek?”
Every backtest ran in its own database holding only earlier data, the prediction's hash was shown hours ago, and a person labeled the answer key before the prediction.
“Isn't this cheating?”
It uses only material professors publish so students can study from it. It tells you where to spend your hours.
“What do you store about students, and who can see it?”
Only what they give it: preferences, syllabus, feedback. Each student has their own dataset and collection; nobody else can read them.
“Where's the compounding?”
Points covered rises across runs; the cost to load a course falls once it's replayed; first-try checks rise; and a student's next answer changes after their feedback.
“Who pays?”
Students and tutoring companies first — and professors: “your exam tests topic X three times more than your lectures did.”
